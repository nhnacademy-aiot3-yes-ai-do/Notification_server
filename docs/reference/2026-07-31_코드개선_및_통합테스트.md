# 2026-07-31 Notification Service 변경 및 검증 기록

## 1. 작업 목적

Grok 코드 리뷰에서 제안한 항목 중 ERD나 다른 서비스의 이벤트 계약을 변경하지 않고 적용할 수 있는 안정성 개선을 반영했다.

이번 작업 범위는 다음 세 가지다.

1. `source_event_id` UNIQUE 충돌을 정상 중복 이벤트로 처리
2. 재시도 정책을 최대 3회로 단일화
3. RabbitMQ Consumer 로그를 오류 유형별로 구분

외부 RabbitMQ 이름, Producer JSON, Telegram·Discord 인증정보, Gateway 계약은 변경하지 않았다.

## 2. 중복 이벤트 처리

### 2.1 문제

Consumer가 먼저 `existsBySourceEventId()`를 확인하더라도 동시에 같은 이벤트가 들어오면 두 Consumer가 모두 “없음”을 확인할 수 있다.

```text
Consumer A: 없음 확인
Consumer B: 없음 확인
Consumer A: 저장 성공
Consumer B: 저장 시도 중 UNIQUE 충돌
```

이때 B를 일반 실패로 처리하면 이미 정상 처리된 메시지가 불필요하게 DLQ로 이동한다.

### 2.2 개선 방식

`NotificationEventService.isProcessed(UUID eventId)`를 추가했다.

Consumer에서 `DataIntegrityViolationException`이 발생하면:

```text
1. 해당 eventId가 실제로 저장됐는지 다시 조회
2. 저장되어 있으면 정상 중복으로 로그를 남기고 종료
3. 저장되어 있지 않으면 실제 DB 오류로 판단하고 DLQ 처리
```

이 방식은 기존 `notification.source_event_id UNIQUE` 제약을 그대로 사용하므로 ERD나 Migration 변경이 없다.

## 3. 재시도 정책 단일화

### 3.1 기존 위험

재시도 횟수를 도메인 코드와 환경 설정에서 각각 관리하면 다음과 같은 불일치가 생길 수 있다.

```text
RetryTemplate: 5회
Delivery 도메인 상태: 3회까지만 허용
```

### 3.2 현재 기준

재시도 횟수는 다음 상수를 유일한 기준으로 사용한다.

```java
NotificationDelivery.MAX_ATTEMPT_COUNT = 3
```

발송 흐름은 다음과 같다.

```text
PENDING
→ 1회 발송 시도
→ 실패 후 2회차 시도
→ 실패 후 3회차 시도
→ 성공하면 SENT
→ 3회 모두 실패하면 FAILED + DLQ
```

`application.yml`에서는 재시도 간격만 설정한다.

```yaml
notification:
  retry:
    backoff: ${NOTIFICATION_RETRY_BACKOFF:1s}
```

따라서 `NOTIFICATION_MAX_ATTEMPTS` 환경변수는 더 이상 사용하지 않는다.

## 4. Consumer 로그 분류

### 4.1 계약 오류

잘못된 JSON, 필수 필드 누락, 등록되지 않은 이벤트 유형, 대상 유형 불일치 등을 의미한다.

```text
WARN Notification event contract rejected
```

### 4.2 기준 설정 오류

이벤트는 올바르지만 해당 이벤트나 채널에 사용할 템플릿이 없거나 기준 데이터가 빠진 경우다.

```text
ERROR Notification event configuration failed
```

### 4.3 영속화 오류

DB 저장 실패나 제약조건 위반이다. 단, `source_event_id`가 이미 저장되어 있는 UNIQUE 충돌은 정상 중복으로 별도 처리한다.

```text
INFO  Duplicate notification event ignored after unique constraint
ERROR Notification event persistence failed
```

### 4.4 시스템 오류

위 유형으로 분류되지 않는 예상하지 못한 내부 오류다.

```text
ERROR Notification event system processing failed
```

### 4.5 로그 보안 원칙

추적용 식별자는 기록한다.

- `eventId`
- `eventType`
- `targetType`
- `targetId`

다음 정보는 기록하지 않는다.

- Telegram Bot Token
- Discord Webhook 전체 주소
- Telegram Chat ID
- JWT, access token, refresh token
- 민감한 payload 원문

## 5. 통합 테스트

### 5.1 실행 환경

- Docker 컨테이너: `notification-db-verify`
- PostgreSQL: 16.14
- 포트: `55432`
- 데이터베이스: `notification_migration_test`

### 5.2 실행 명령

```bash
mvn \
  -Dnotification.integration.enabled=true \
  -Dnotification.integration.db-url=jdbc:postgresql://localhost:55432/notification_migration_test \
  -Dnotification.integration.db-username=postgres \
  -Dnotification.integration.db-password=postgres \
  test
```

## 6. 아직 남은 작업

이번 변경으로 외부 계약까지 확정된 것은 아니다.

- 실제 RabbitMQ exchange·queue·routing key·vhost 확정
- Producer별 최종 JSON payload 확정
- Telegram Bot Token과 Discord Webhook 연결
- Cultivation·Inquiry 소유권 확인 API 연결
- Config/Kubernetes 최종 서비스명 확인
- 실제 RabbitMQ 이벤트 1건 통합 테스트

위 항목은 다른 담당자와 계약을 확정한 뒤 진행한다.
