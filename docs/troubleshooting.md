# Notification Server 트러블슈팅 회고

Notification Server에서 겪은 설계 및 연동 문제를 당시 확인한 사실과 기억을 구분해 기록합니다.

## 김동건 — 알림 이벤트·ERD 설계·Telegram 연동

Notification에서는 RabbitMQ 이벤트를 받아 유형별로 분류하고 발송에 필요한 데이터로 처리하는 흐름과 ERD 설계를 주로 맡았습니다. 실제 이메일·Telegram 발송 로직은 다른 팀원이 담당했으므로, 아래 내용은 이벤트 수신부터 발송 준비까지의 경험을 중심으로 정리했습니다.

### 1. 이벤트 종류가 늘면서 ERD 관계와 조회 조건을 다시 설계한 경험

**문제 상황**
처음에는 두 종류의 이벤트만 처리하는 단순한 흐름으로 시작했습니다. 이후 확장성을 고려해 수신·분류·처리 구조를 나누기 시작했고, ERD도 함께 다시 살펴봤습니다. 테이블을 만드는 일은 어렵지 않았지만, 저장 시 필요한 참조 조건을 어떻게 보장하고 조회 시 원하는 데이터를 어떻게 쉽게 가져올지 고민이 컸습니다.

초기에는 관계가 명확하지 않은 값도 컬럼으로 두고, 해당 값이 실제로 존재하는지는 애플리케이션에서 검사하면 된다고 생각한 부분이 있었습니다. 이후 관리자 화면에서 항목을 추가·수정하거나 사용자가 구독할 때 조건을 표현하기 어렵고, 조인과 조회 조건으로 필요한 데이터를 가져오기도 쉽지 않다는 점을 발견했습니다.

**원인**
초기 ERD는 당장 처리할 두 이벤트의 저장 형태에 맞춰졌고, 이후 필요한 관리·구독 흐름과 조회 방식을 충분히 반영하지 못했습니다. 값의 존재 여부만 검사하는 방식으로는 데이터 사이의 관계와 제약을 모델에 드러내기 어려웠습니다.

**해결**
ERD Cloud에서 테이블 배치와 관계를 다시 정리했습니다. 제가 설계한 ERD를 구현을 맡은 팀원과 AI에 전달해 그 방향으로 관계 매핑을 수정하도록 요청했습니다. 어떤 관계를 저장 시 보장하고, 어떤 관계를 조인해 관리·구독 조회에 사용할지도 함께 검토했습니다.

**배운 점**
ERD는 테이블을 나열하는 데서 끝나지 않고 생성·수정 시 지켜야 할 조건과 실제 조회·조인 방식을 함께 표현해야 합니다. 초기에 단순 컬럼으로 둔 값도 관리 화면과 구독 흐름에서 어떻게 검증하고 조회할지 살펴본 뒤 관계를 정하는 것이 중요했습니다.

### 2. 업스트림 응답을 전달했을 때 브라우저 화면 이동이 되지 않은 문제

**문제 상황**
Telegram 연동 흐름에서 Front가 업스트림 응답을 브라우저에 전달했을 때, 브라우저가 응답을 정상 처리하지 못해 화면 이동이 되지 않는 문제가 있었습니다.

**원인**
정확히 어떤 헤더가 문제였는지는 확인하지 못했습니다. 비슷한 사례를 AI와 살펴본 뒤 업스트림 응답의 중복 헤더가 원인일 수 있다고 추정했습니다. 확인된 근본 원인이 아니라 당시의 추정으로 기록합니다.

**해결**
업스트림 응답을 그대로 전달하는 대신 상태 코드와 본문을 읽어 새 응답을 만들도록 Front에 공통 유틸리티를 뒀습니다. 필요한 경우 `Location` 헤더만 선택적으로 유지하고 나머지 업스트림 헤더는 전달하지 않도록 했습니다. 공통 처리 적용 후 브라우저 화면 이동이 동작했습니다.

**배운 점**
프록시나 BFF가 업스트림 응답을 브라우저에 전달할 때 헤더를 무조건 복사하지 않고, 클라이언트에 필요한 상태·본문·헤더를 구분해 응답을 구성해야 합니다.

### 3. Telegram `/start` webhook의 Gateway 경유 경로를 조정한 경험

**문제 상황**
Telegram의 `/start` webhook 요청이 Gateway를 경유해 Notification으로 전달되도록 연결했지만, 기대한 대로 수신·처리되지 않는 일이 있었습니다.

**원인과 해결**
요청은 Gateway를 경유하도록 구성했습니다. 문제는 주소 또는 경로 설정과 관련된 것으로 어렴풋이 기억합니다. Gateway 자체를 수정한 것은 아니며 Front 또는 Notification 쪽 설정이나 처리 경로를 손봤던 것 같습니다. 정확한 잘못된 주소와 수정 파일은 기억만으로 특정하기 어려워 단정하지 않습니다.

**배운 점**
Webhook은 외부 서비스가 호출하는 주소부터 Gateway 라우팅, 수신 서비스의 경로까지 이어서 확인해야 합니다. 당시 기록이 부족해 원인과 수정 지점을 정확히 재현하기 어렵다는 점도 남깁니다.
